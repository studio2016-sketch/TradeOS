# Forward-only forecast source chronology repair

Current main (73fd8f084de0615086a11b6c103ba6cc2c2da443) correctly blocks scientific eligibility with V3_RESOLVER_PROTOCOL_MISMATCH. Its shadow writer nevertheless writes the challenger decision record's later recorded_at into source verification's forecast_created_at. Baseline and challenger also compare and persist evidence clocks through JavaScript Date, losing submillisecond chronology.

This narrow repair reads source event/receipt and each forecast's INSERT RETURNING creation time as PostgreSQL text. Both verification inserts require exact event <= receipt <= actual forecast creation using the existing nanosecond parser, and retain the supplied timestamp strings. The immutable decision record's insertion time cannot substitute for either prediction's creation boundary. Invalid or missing verification clocks fail closed. The model's descriptive feature calculations and checksums retain their existing Date-based representation. No historical row is updated or backfilled.

The actual writer regression harness mocks only its database boundary. Four new timing regression groups fail on unchanged main and pass after repair: exact fractional clock retention; later decision-record substitution; submillisecond lookahead/reversed source chronology; and separate baseline/challenger creation boundaries. Equal boundaries, timezone-offset equivalence, malformed receipts and invalid forecast dates are covered. Another regression verifies that the shared supplemental IEX entry is selected before either forecast and without querying outcome availability. Existing source-selection, fixed fifteen-minute-grace and scientific-containment tests remain applicable. Synthetic software tests do not establish source publication authenticity, database permissions, provider coverage or predictive validity.

## Release prerequisites and limits

This repair alone does not resolve the v3 protocol mismatch, atomically create forecast pairs, activate v4, or certify a cohort. Existing v3 outcomes and bindings stay descriptive. Even exact creation text is a stored database boundary, not proof of physical time, commit visibility or non-backdating. The current writer still creates forecasts and immutable records in separate statements. Its source verification concerns the selected last trend observation; it does not certify every lookback row or the supplemental quote capture.

Before releasing this repair, review final-head CI and exercise the exact SQL/transport timestamp roundtrip on an authorized disposable staging database. Then obtain separate merge/release approval. Branch-specific automatic Vercel deployment is disabled; no migration or new production collector run is part of this change.

Before any conforming prospective protocol activation: finish the existing dedicated binding design with restricted atomic writes and server-owned insertion clocks; test rollback, idempotency, concurrent writers, nonowner permissions and attempted backdating on real PostgreSQL; freeze a separately approved protocol and activation boundary; make dispatcher, append-only outcome persistence and cohort readers version aware; independently validate resolver conformance and source provenance/coverage. Do not mix or rewrite historical cohorts. Preserve the scientific blocker, fifteen-minute grace and live-execution prohibition until the separately required approvals and evidence exist.

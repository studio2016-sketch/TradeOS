# Lossless slippage and bounded daily collection: inactive preparation

Stacked on draft PR #98 at `1a3e3177dc4e02f5fdf68481c4df84c44189664c`. This adds no production route, cron, CLI execution or default database connection. The existing intraday route continues using its original microsecond guard until a separate reviewed activation. Outcome validation and historical records are untouched.

## Exact timestamp storage

`db/migrations/20261116_exact_factor_evidence.sql` creates an independent append-only table with original timestamp strings and integer `numeric(30,0)` nanoseconds. `bigint` cannot represent all years supported by the existing parser. A strict SQL parser independently checks both representations, calendar validity and observation <= availability. Value and timestamp precision are never deliberately rounded. Duplicate identity uses exact instants, not truncated timestamps. Updates, deletes and truncation fail. The migration creates no legacy-table view and rewrites no old rows.

`persistExactEvidenceWithSql` applies the existing intake gate, stores exact strings/integers, treats identical retries as no-ops and reports conflicting immutable identities instead of overwriting them. SQL failures propagate. `readExactEvidenceAtDecisionWithSql` scopes reads by subject, compares integer nanoseconds, checks readback consistency and fails if its bounded result is incomplete. It reads only the exact lane; it does not claim legacy evidence coverage or independent source-time certification.

`persistIntradayWithExactSlippage` is the prepared, currently unused activation boundary. All new slippage goes to the exact lane; other intraday factors retain existing storage. Its receipt reports saved counts by lane. It does not dual-write rounded copies. A failure can occur after another factor was saved, as in the existing per-candidate writer: preserve the error and use idempotent retry, never assume atomic whole-collector success.

## Bounded daily collection

`runPreparedDailyFactorCollection(sql)` binds the existing Alpaca history adapter to the new collector and store, but is not called by any route or schedule. Only the existing IEX feed is supported; a different configured feed fails before a claim. Fixed subjects are NVDA, AMD and PLTR, not the old rotating 100-symbol universe. Maximum three requests, concurrency two, existing 12-second transport timeout, 800-day/1,000-bar request bound, no pagination continuation and no retries.

Expected completed sessions use the repository's reviewed, pinned 2026 IEX calendar, including DST, full closures and early closes. Dates before calendar capture or outside 2026 fail closed. A 15-minute operational finalization wait follows the latest close; during that wait the collector refuses to substitute the prior session. This wait does not certify provider finality. A claim expires after at most two minutes or at the next session close, whichever comes first. Both application and database wall clocks enforce expiry; clocks moving backwards abort.

Every accepted history must have the latest expected session, valid finite OHLCV, unique exact New York midnight labels, the supported feed, and no missing trading sessions in the calculation window. The last at most 200 complete sessions are used, and the entire calculation window must be covered by the pinned calendar if 200 bars are supplied. Short history produces only factors whose windows exist. All 24 keys may therefore remain unavailable for an unusable source. No stale daily label is refreshed by receipt time. The unchanged engine runs under a distinct collection policy with the exact input count, digest, retained input bars and provider daily label. Recursive indicators can differ from the old collector's longer input windows; new policy provenance must not be erased or treated as historical method equivalence.

Availability is sampled after all retrieval and calculations, not at the request start. The daily bar timestamp remains the provider's session label, with actual close separately recorded; it is not a claim that final closing prices were known at midnight. Stored observations remain research-only and uncertified.

`db/migrations/20261116_daily_factor_claims.sql` adds immutable claim/completion tables. The primary session key permits only one durable attempt, even across processes or future policy changes. Failed/uncertain attempts are consumed and require operator investigation rather than automatic retry. Completion and at most 72 new legacy evidence rows are one SQL statement, so a failed insert or competing completion rolls back that finalization. The store independently recalculates the proposed factor values from retained input bars before insertion. No old receipt or evidence row is updated.

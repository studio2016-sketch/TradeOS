# Provider news timestamp intake

The Alpaca and Massive HTTP adapters previously substituted the server's current time when a source timestamp was missing. That made an undated article appear fresh before stricter evidence validation ran. Some malformed response fields were also coerced into strings or treated as empty success.

`decodeProviderNews` is now the shared source boundary. It requires a valid explicit receipt clock and an article array in a non-error-bearing response. Malformed articles are individually rejected with static indexed reasons; malformed response envelopes remain failures. An explicit empty article array remains a valid empty response.

New articles require stable identity, nonblank textual headlines, valid symbol arrays and textual optional summaries. Invalid symbols reject the article rather than silently turning a multi-issuer report into a single-issuer report. Timestamps must carry a timezone and pass strict calendar validation. Source times after receipt, contradictory Alpaca creation/update ordering, unsupported PostgreSQL offsets and nonzero submicrosecond storage precision are rejected before cache insertion. No missing clock is inferred from retrieval time, an article ID or another malformed field.

The Alpaca adapter retains its existing latest-version convention: use updated_at when present, otherwise created_at. Any supplied creation/update field must validate, and update time must not precede creation time. Alpaca documents these as separate creation and update clocks; this convention is not a certificate of original publication time. Massive uses its explicit published_utc. Receipt/completion availability remains separate from these source clocks. Provider references: [Alpaca news fields](https://docs.alpaca.markets/us/docs/streaming-real-time-news) and [Massive news](https://massive.com/docs/rest/stocks/news).

Ingestion receipts now retain raw received count, accepted count, indexed rejection reasons and `tradeos.provider-news-intake.v1`. They do not log raw payloads or claim source authenticity. Only accepted rows reach the existing cache writer. Historical cache rows and immutable evidence are neither rewritten nor automatically marked as validated under this policy. Existing cache fallback behavior remains; a historical cached row does not acquire independently verified timing merely because it passes current extraction checks.

Ten new regression groups cover missing/invalid/future clocks, exact update ordering, cache-safe precision/offsets, envelope errors, identity/content validation, malformed sibling isolation and the actual decoder-to-watchlist-to-persistence path. A mocked HTTP integration test also executes both real provider adapters and verifies that undated articles do not reach SQL cache writes and that ingestion diagnostics retain raw/accepted counts. No live provider requests, production collector calls, database migrations or production evidence writes are made by these tests.

The complete local suite passed 473 tests, TypeScript and the production build. A temporary compatibility run with pending PR #81 at `c26f94c` passed 493 tests and TypeScript; its inactive resolver code is not included in this proposal. A corrupt local Turbopack cache was removed before the successful build; no source or persistent database was removed. Final-head GitHub CI remains a separate verification step.

This is validation of source-reported inputs, not independent origin authentication, proof of historical availability, provider completeness or predictive certification. The source cache remains mutable. The pending database constraint remains unapplied; outcome activation, promotion and paper-only execution restrictions are unchanged.
